🔭 Astro Portfolio — Slug-Based Architecture

How photo URLs work without ever exposing Immich asset IDs to the browser

1. The Big Picture

Instead of showing ugly UUIDs in the URL, we use human-readable slugs (like rosette-nebula). The slug is resolved to the real ID only on the server.

Key insight: The browser never sees the UUID. It only knows about slugs like rosette-nebula. The UUID (c3629bd3-6919-...) exists only in server-to-server communication.

4. Route Map

Here are all the API routes and what they do:

Route Purpose
/api/portfolio Returns all photos with slugs, titles, and slug-based image URLs
/api/portfolio/lookup?slug=... Converts a slug → Immich UUID (server-side only)
/api/image/by-slug/[slug]/thumbnail Returns thumbnail image (small, for gallery grid)
/api/image/by-slug/[slug]/preview Returns preview image (medium, for detail page)
/api/image/by-slug/[slug]/original Returns original full-res image (for download)
/api/photo/[uuid]/metadata Returns EXIF/camera data (called server-side by photo page)
Security benefit: Since UUIDs are never exposed to the browser, an attacker cannot enumerate or guess Immich asset IDs to try to access photos outside the portfolio album.
How slugs are generated: The photo title (from EXIF data or filename) is converted to lowercase, spaces become hyphens, and special characters are removed. Example: "Rosette Nebula (NGC 2237)" becomes rosette-nebula-ngc-2237. If two photos have the same title, a number is appended: rosette-nebula-2.
